What is new in the release

Declarative, cross-platform UI in Rust

FerroUI is a cross-platform UI framework for Rust. An interface is written in declarative Rust: builders for every control, the rsx! macro, fine-grained signals and React-like components with hooks and a reconciler. It can also be written in XAML compiled to Rust. Both drive one control library with data binding, themes for five design languages and GPU rendering, on macOS, Windows, Linux, iOS, Android and the browser.

Declarative Rust

A component that runs again when its signal changes; the reconciler patches the text. From the README.

src/main.rsrust
use ferroui_base::layout::Orientation;
use ferroui_view::prelude::*;

#[component(rerender)]
fn Counter() -> Element {
    let count = use_signal(|| 0);
    rsx! {
        StackPanel { orientation: Orientation::Horizontal, spacing: 8.0,
            TextBlock { text: format!("Clicked {} times", count.get()) }
            Button { class: "accent", on_click: move |_| count.update(|c| *c += 1), "Click" }
        }
    }
}

fn main() {
    ferroui_view::launch(|| rsx! { Window { title: "Counter", Counter {} } });
}

Declarative Rust UI

Signals and React-like components, in Rust

ferroui-view writes user interfaces in plain Rust, on the same controls, themes, styles and bindings as markup. A component can run once and let its properties follow signals, in the manner of SolidJS and Leptos, or run again when its state changes and let a reconciler patch the controls, in the manner of React. Components of both kinds are children of each other.

The counter of 7GUIs as a component that runs again: its state is a hook, the function runs again when the count changes, and the reconciler patches the text of the field. From samples/SevenGuis.

counter.rsrust
use ferroui_base::layout::Orientation;
use ferroui_view::prelude::*;

#[component(rerender)]
pub fn Counter() -> Element {
    let count = use_signal(|| 0);
    rsx! {
        StackPanel { orientation: Orientation::Horizontal, spacing: 8.0,
            TextBox { text: count.get().to_string(), is_read_only: true, width: 80.0 }
            Button { on_click: move |_| count.update(|c| *c += 1), "Count" }
        }
    }
}

The same counter with the builders, without macros: one builder per control and one setter per property and routed event, generated from the sources of the controls.

counter.rsrust
use ferroui_base::layout::Orientation;
use ferroui_view::prelude::*;

pub fn counter() -> Element {
    let count = signal(0);
    stack_panel()
        .orientation(Orientation::Horizontal)
        .spacing(8.0)
        .child(text_box().text(count).is_read_only(true).width(80.0))
        .child(button().content("Count").on_click(move |_| count.update(|c| *c += 1)))
        .into()
}

A keyed list and conditions in rsx!: the item of a todo that stays keeps its controls, and TodoItem runs again only when its todo changes. From samples/TodoMvc.

view.rsrust
#[component(rerender)]
fn TodoList(todos: Signal<Todos>, filter: Filter) -> Element {
    let (visible, all_completed, any) =
        todos.with(|list| (list.visible(filter), list.all_completed(), !list.is_empty()));

    rsx! {
        StackPanel { spacing: 8.0,
            if any {
                CheckBox { name: "ToggleAll", is_checked: all_completed,
                    on_click: move |_| todos.update(|list| list.set_all_completed(!all_completed)),
                    "Mark all as complete" }
            }
            StackPanel { name: "Todos", spacing: 2.0,
                for todo in visible {
                    TodoItem { key: todo.id, todo, todos }
                }
            }
            if any {
                Footer { todos, filter }
            }
        }
    }
}

Builders and rsx!

A builder for every control, generated from the sources of the controls, and the rsx! macro for the tree, with attached properties, text, conditions and loops. A misspelled or mistyped attribute is a compile error.

Declarative UI

Fine-grained signals

Signals, memos and effects. A property follows a signal or a closure and updates without running anything else; values can be two-way, and keyed lists, conditions and computed children follow state (for_each, show, dynamic).

State

Components and hooks

Function components with use_signal, use_memo, use_effect, use_effect_with and use_hook; provide_context and use_context hand values to the components below.

HooksCompared with React

A reconciler

Siblings are matched by key and by place, equal values are left alone, handlers are swapped in place, and keyed lists are reordered with the fewest moves. A component with comparable parameters is memoized by default.

Reconciler

Async data, errors, navigation

use_future with suspense for data that arrives later, error_boundary for a part of the window that fails without ending the application, and a router with routes and parameters.

Larger applications

Styles, themes and motion

Styles with XAML selectors, the theme variant and resources followed live, transitions and key-frame animations, popups and context menus as elements, and virtualized lists whose items are components.

Styles and motion

Hot reload and an inspector

With the feature hot-reload, the literals of rsx! are edited while the application runs and state, focus and scroll positions stay. Debug builds report missing keys and runaway components, and Shift+F12 opens an inspector of the components.

ToolsHot reload engine

The complete mapping, where the two behave alike and where they differ, and what React has that FerroUI does not have yet are in declarative-ui-react.md.

Compiled XAML

Or write the views in XAML, compiled to Rust

Markup is the second way to write an interface, on the same controls, themes and bindings. The build script of a crate compiles it to Rust source; it can also be loaded at run time. Rust components and XAML views can be placed inside each other.

Compiled, or loaded at run time

XAML documents are compiled to Rust by the build script of the crate, with the framework's markup extensions; the run-time loader reads the same markup, and XAML reloaded at run time keeps supported live components.

XAML design

Compiled bindings

Compiled {x:Bind} and compiled bindings by default, with converters, multi-bindings, data validation and templates; reflection-style binding paths remain available.

x:Bind

Themes trimmed to the application

Themes are compiled XAML, and an application keeps only the units of its theme it uses. A code-only application names its theme in a build script of one statement.

Compiled XAML themes

Rust and XAML together

A component in XAML (ComponentHost, register_component), XAML in a component (use_xaml), and the data context of a view model in a component (use_data_context).

Get started

From cargo new to a window

FerroUI is a set of crates released together at one version. Name the same version for every FerroUI crate, or generate a project from one of the templates.

  1. Install the requirements

    • Rust 1.89 or later (the browser needs 1.93 or later).
    • The first build downloads a prebuilt Skia for the target, or builds it from source where no prebuilt binary matches (Vulkan on Windows), and builds HarfBuzz from source with a C++ compiler; it can take a while.
    What each platform needs
    PlatformNeeds
    macOSmacOS 11 or later and the Xcode command line tools (the platform compiles an Objective-C++ library).
    Windowsx64 or ARM64, the MSVC build tools; libclang for ANGLE (the default feature angle); the feature vulkan builds Skia from source. Hosting in WinUI 3 needs the Windows App SDK 1.6 runtime and its bootstrap library beside the executable.
    LinuxThe development packages of fontconfig and FreeType. The system libraries (Xlib, GTK, GLib, EGL, Vulkan, Wayland, xkbcommon, libinput, libdrm, libgbm) are opened at run time; none is linked.
    iOSXcode with the iOS SDK and the targets aarch64-apple-ios and aarch64-apple-ios-sim; an application is bundled without an Xcode project (scripts/ios/bundle.sh).
    AndroidThe Android SDK and NDK, stable Rust with the target aarch64-linux-android, API level 26 or later; packaged without Gradle (scripts/android/apk.sh).
    BrowserThe target wasm32-unknown-emscripten, Emscripten and the pinned wasm-bindgen command-line tool (scripts/browser/setup.sh installs them).

    Hello, World! in the WinUI 3 theme: with rsx! and a signal, in XAML, and with Rust objects.

    A component with a button that counts its clicks; the count is a signal that the text of the button follows. From samples/HelloWorld.Macros.

    Cargo.tomltoml
    [dependencies]
ferroui-base = "={{version}}"
ferroui-view = { version = "={{version}}", features = ["desktop"] }
ferroui-themes-winui = "={{version}}"
    Terminalsh
    cargo new hello-ferroui
cd hello-ferroui
cargo run
    src/main.rsrust
    use ferroui_base::layout::{HorizontalAlignment, VerticalAlignment};
use ferroui_view::prelude::*;

/// The content of the window.
#[component]
fn Hello() -> Element {
    let clicks = signal(0);
    rsx! {
        StackPanel { horizontal_alignment: HorizontalAlignment::Center, vertical_alignment: VerticalAlignment::Center, spacing: 12.0,
            TextBlock { text: "Hello, World!", font_size: 28.0 }
            Button { name: "Count", horizontal_alignment: HorizontalAlignment::Center, on_click: move |_| clicks.update(|c| *c += 1),
                TextBlock { text: move || clicked_text(clicks.get()) }
            }
        }
    }
}

/// The text of the button after `clicks` clicks.
fn clicked_text(clicks: i32) -> String {
    match clicks {
        1 => "Clicked 1 time".to_string(),
        _ => format!("Clicked {clicks} times"),
    }
}

fn main() {
    launch_themed(
        || ferroui_themes_winui::WinUITheme::new().as_style(),
        || window().title("Hello, World!").width(400.0).height(240.0).child(Hello()).into(),
        |_| {},
    );
}

    An application class that creates its window when the framework has finished initialising, with everything from the prelude of the facade crate and the WinUI 3 theme (its feature winui-theme). The example hello.rs of the repository is the complete program.

    Cargo.tomltoml
    [dependencies]
ferroui = { version = "={{version}}", default-features = false, features = ["desktop", "winui-theme"] }
    src/main.rsrust
    use ferroui::prelude::*;
use std::rc::Rc;

#[repr(C)]
pub struct App {
    base: Application,
}

ferro_class!(App: Application);
ferro_impl_classes!(App: FerroObjectImpl);

impl NewApplication for App {
    fn new_application() -> Ref<Self> {
        instantiate(Self { base: Application::construct() })
    }
}

impl ApplicationImpl for App {
    fn initialize(this: &Self) {
        Self::parent_initialize(this);
        this.styles().add(WinUITheme::new().as_style());
    }

    fn on_framework_initialization_completed(this: &Self) {
        let lifetime = this.application_lifetime();
        if let Some(desktop) =
            lifetime.as_ref().and_then(|lifetime| lifetime.as_classic_desktop_style_application_lifetime())
        {
            desktop.set_main_window(Some(create_main_window()));
        }
        Self::parent_on_framework_initialization_completed(this);
    }
}

fn create_main_window() -> Ref<Window> {
    let text = TextBlock::new();
    text.set_text(Some("Hello from FerroUI"));
    text.set_font_size(24.0);

    let button = Button::new();
    button.set_content(Some(Rc::new("Click me".to_string())));
    button.click(|_, _| println!("Button clicked"));

    let panel = StackPanel::new();
    panel.set_spacing(12.0);
    panel.children().add(text);
    panel.children().add(button);

    let window = Window::new();
    window.set_title(Some("Hello".to_string()));
    window.set_content(Some(Control::boxed(panel)));
    window
}

fn main() -> std::process::ExitCode {
    let args: Vec<String> = std::env::args().skip(1).collect();
    let exit_code = AppBuilder::configure::<App>()
        .use_platform_detect()
        .start_with_classic_desktop_lifetime(&args);
    std::process::ExitCode::from(exit_code as u8)
}

App template

An application in a repository of its own

Solitaire, Ember, FerroDesign and Calculator are set up this way: FerroUI as a git submodule, its workspace dependencies and profiles copied into the application's workspace, and FerroUI's reusable workflow for CI and GitHub Pages. The guide is docs/apps.md. The cross-platform template generates this layout with desktop, browser, Android and iOS hosts.

Project status

Where FerroUI stands

FerroUI runs on macOS, Windows, Linux (X11, Wayland and the framebuffer), iOS, Android and in the browser. It was verified in continuous integration, in virtual machines, in the iOS simulator and on the Android emulator, not on a range of real devices.

API within 0.5

Within 0.5 the public API is kept; 0.6.0 may change it. The work towards the next version is published as previews, which may change any part of the public API.

Declarative UI: phases 0 to 6 built

Builders, rsx!, signals, components with hooks, the reconciler, XAML interoperation, tools, performance and scale, and futures, error boundaries and a router; what React has that it does not have yet is listed in declarative-ui-react.md.

Skia is the reference

Skia is the default and reference renderer, with HarfBuzz for text shaping.

Vello is experimental

The Vello backend has CPU, hybrid and GPU modes and is measured against Skia; its open work is in vello-backend.md.

Hot reload is experimental

A development engine with explicit adapters and release gates; parts of the build integration of XAML are open.

Origins

Where FerroUI comes from

FerroUI started as a port of a .NET UI framework to Rust, and its object model, styling, layout, input and composition architecture follow that design; the XAML compiler front end comes from XamlX. Applications, themes and markup written against that model carry over with their structure. Other parts are native ports of their own sources: the WinUI 3 controls, theme and composition API, Xaml.Behaviors, the TreeDataGrid, LiveCharts2, Rx.NET, DynamicData, ReactiveUI and Splat.

The declarative Rust layer, compiled {x:Bind}, theme trimming, the Material 3 and macOS 26 themes, the portable media stack, 3D and the performance work are FerroUI's own.

What follows a source is tracked against it, member by member, in TRACKING.md, and every difference is recorded in DEVIATIONS.md. The projects and their licences are named in the Origins section of the README and in NOTICE.md.
